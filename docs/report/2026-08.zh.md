# dsh 插件生态还没有权限模型

**DeepSeek Harness 插件生态能力普查 —— 2026 年 8 月**

*[English](2026-08.md) · 数据:[dsh-xray](https://unstone.github.io/dsh-xray/) · 方法:静态分析,不执行任何代码*

---

## 摘要

`dsh-plugin` 标签在 30 天内从约 200 个仓库涨到 **7,000+**。我们对星标最高的一批做了静态扫描,发现绝大多数带有"强能力面":能改写系统提示词、拦截 API 流量、起子进程,或者给运行时本体打补丁。

但结论不是"插件很危险",而是:

> **插件并没有越权。因为根本不存在可越的权限。**

dsh 没有插件级的权限声明,也没有对应的运行时强制。`inject` 字段解决的是加载顺序和依赖解析,不是授权。装一个插件,它要什么上下文就得到什么,而安装路径上没有任何东西告诉你这意味着什么。

对一个高速生长的生态来说,这是很正常的阶段。npm 也经历过。而这恰恰是纠正成本最低的阶段——所以值得现在就把它讲清楚。

## 发现 1 —— 强能力是常态,不是例外

<!--STATS_LEVELS-->
| 等级 | 含义 | 数量 | 占比 |
|---|---|---|---|
| **C3** | 强能力 + 敏感行为 | 2920 | 40% |
| **C2** | 强能力(其一) | 3548 | 49% |
| **C1** | 常规 | 506 | 7% |
| **C0** | 无显著能力面 | 291 | 4% |

**89% 的插件带强能力面(C2+),40% 同时存在敏感行为(C3)。**
<!--/STATS_LEVELS-->

样本从 80 扩到 169、480,再到 3,972 的过程中,C2+ 占比走了 80% → 85% → 90% → 91%。我们本以为长尾会把这个数字拉下来。并没有。

长尾改变的是这条带子**内部**的构成:把它算进来之后,落在 C2(只占一项强能力)的插件多于 C3(强能力叠加敏感行为)。也就是说,一个典型的长尾插件一次性握的东西少一些——但它带有强能力的概率一点不低。

覆盖率:标签下 7,010 个仓库,我们持有 3,972 张卡片。**2 星以上的仓库全部覆盖**,1 星以上的 4,115 个覆盖了 4,092 个;剩下的缺口是零星标长尾,排队等后续轮次。另有 120 个仓库不含可扫描代码。

## 发现 2 —— 给宿主运行时打补丁是常规操作

<!--STATS_PATCH-->
**5566 个插件(77%)通过 `manifest.bundle.patch` 给 dsh 运行时本体打补丁。**

星标最高的几个:

- [amruthpillai/reactive-resume](https://github.com/amruthpillai/reactive-resume) — 41,041★
- [volcengine/OpenViking](https://github.com/volcengine/OpenViking) — 29,503★
- [tt-a1i/archify](https://github.com/tt-a1i/archify) — 14,256★
- [EverMind-AI/EverOS](https://github.com/EverMind-AI/EverOS) — 12,149★
- [Q00/ouroboros](https://github.com/Q00/ouroboros) — 5,558★
<!--/STATS_PATCH-->

`manifest.bundle.patch` 指向一个 `cordis.patch.yml`,在加载时修改 dsh 核心行为。这是整个系统里最深的供应链面——比任何工具调用都深,因为它改的是那个裁决工具调用的宿主本身。

在多数包生态里,给宿主运行时打补丁是需要专门理由的例外动作。而在这里,它是普通 UI 插件和效率插件都在用的常规集成手段。安装流程和插件列表都不会提示这件事。

## 发现 3 —— manifest 描述不了插件的行为

以一个 4,300 星的 UI 插件为例,它 manifest 里的 `client.inject` 是这样的:

```json
["@deepseek-ai/dsh-client-runtime", "@deepseek-ai/dsh-client-locale", "…"]
```

这些是 npm 包依赖。而它的代码实际获取了 **17 个运行时服务**,其中包括 `systemPrompt`、`apiProxy`、`subprocess`、`webServer`,并挂上了 `system-prompt/assemble` 和 `api/gate` 两个钩子。

这里没有任何欺骗:`inject` 本来就是用于依赖解析和加载顺序的,它把自己的活干得很好。问题在于:**manifest 里没有任何字段是用来描述能力的**。一个用户把 manifest 逐行读完,依然无从得知这个插件能改写提示词、能拦截 API 流量——这些信息只存在于代码里。

## 发现 4 —— 凭证面很宽,且大多正当

<!--STATS_TOKEN-->
**681 个插件(9%)读取凭证类环境变量**(名称含 KEY/TOKEN/SECRET/PASSWORD 等),涉及 AWS、阿里云 OSS、GitHub、各家模型 API 等。
<!--/STATS_TOKEN-->

存储插件读 `AWS_ACCESS_KEY_ID`、模型路由插件读 `DEEPSEEK_API_KEY`,这正是它们存在的意义。问题不在于它们读凭证,而在于:**一个本不该读凭证的插件,在安装那一刻长得一模一样。**

## 这份报告不是什么

我们没有发布恶意插件名单。我们没有发现恶意证据,也没有去找——静态能力分析无法判定意图。

能力等级(C0–C3)衡量的是**能力面大小与透明度**,不是危害风险。评级最高的项目里有几个恰恰是生态中工程质量最好的:一个桌面外壳或设计工具拿到 C3,通常只是说明它确实需要子进程和本地服务来完成本职工作。

我们真正关心的区别是:**一个需要强能力的插件**,和**一个拥有强能力却没人注意到的插件**——而今天从外部看,这两者毫无分别。

## 怎么修

按对生态的改动成本从低到高排:

| # | 改动 | 责任方 | 成本 |
|---|---|---|---|
| 1 | 安装时展示能力卡片,哪怕只是告知性质 | 注册表、安装工具 | 低 |
| 2 | 给插件 manifest 加一个声明式 `capabilities` 字段,初期不强制 | dsh 核心 | 低 |
| 3 | 对"声明能力"与"实际代码"的偏差告警 | 工具层(本项目) | 中 |
| 4 | C2+ 插件安装需显式同意,就像 `tools/pre-execute` 已经在做的那样 | dsh 核心 | 中 |
| 5 | 在上下文边界强制执行声明的能力 | dsh 核心 | 高 |

第 2 步最关键也最便宜。dsh 其实已经有了第 4 步需要的全部机制——`tools/pre-execute` 返回 `{kind: 'ask'}` 就是这个模式,只是作用在下一层。插件安装从来没有得到过工具执行同等的待遇。

## 方法、局限与复核方式

- **只做静态分析。** 混淆过的或动态构造的行为我们看不见。有心作恶的人可以轻松绕过这个扫描器——那不是我们的威胁模型。我们的威胁模型是:**没人知道普通插件在做什么。**
- **基于正则的检测**会误报(注释里的 `"eval("` 字符串)也会漏报(间接调用)。每条标志都附证据,可以逐条判断。
- **测试代码**不计入风险标志,但计入能力识别。
- **没有可扫描代码的仓库**(纯文档或纯素材)会被标记为未扫描,不会静默丢弃。仓库体积不构成限制:压缩包是流式解析的,素材很重的仓库同样能分析。
- **复现:** `python scanner/discover.py all && cd scanner && python pipeline.py all 12`

更正与申诉:[github.com/unStone/dsh-xray/issues](https://github.com/unStone/dsh-xray/issues)。规则在公开处修正,每日重扫。
