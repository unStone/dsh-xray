## 2026-08-30 · 打包自检脚本不等于插件在执行命令

[Issue #4](https://github.com/unStone/dsh-xray/issues/4) 指出:有个插件因为 `scripts/check-pack.mjs` 里的 `exec` 被判为 C3,而这个脚本被它自己 `package.json` 的 `files` 白名单挡在发布包之外。装这个插件,这个文件根本不会落到磁盘上——命令是开发者跑的,不是用户跑的。

提报者同时还证明了"顺手的修法"是错的,他是对的:按目录名忽略 `scripts/`,会把 [`LBXC-666/dsh-voice-input`](https://github.com/LBXC-666/dsh-voice-input) 藏起来——它明确发布了 `scripts/**/*.mjs`,其中一个代理会开 socket 并读 `DASHSCOPE_API_KEY`。

**要两个证据,不是一个。** 一个文件只有同时满足两条才算"不随包发布的开发工具":它位于工具目录根(`scripts/`、`tools/`、`bench/`,或根目录下 `build.mjs` 形态的构建配置),**并且**有显式 `files` 白名单证明发布包里没有它。任何一条单独用都是错的。只看目录名,会藏掉一些插件真的发布出去的 `scripts/**/*.mjs`;只看是否在包里更糟——TypeScript 插件的 `src/` 通常被 `files` 排除、只发编译产物 `lib/`,而 `lib/` 本来就作为构建产物不计分,两边都降级就等于让这个插件的真实行为彻底消失。

**用 npm 的 glob 语义,不是 `fnmatch` 的。** 在 minimatch 里 `**` 可以跨零个或多个路径段,所以 `scripts/**/*.mjs` 能匹配直接子文件 `scripts/proxy.mjs`;Python 的 `fnmatch` 不能。就是这一处差别,决定了这次改动是修正还是掩盖。这套翻译——globstar、`*` 不跨 `/`、字符类、花括号展开,以及 `main`/`bin`/`directories.bin` 的强制包含——已用 npm 11 的 `npm pack --dry-run --json` 逐条核对,核对结果作为测试表固化下来,CI 不需要装 npm 也能守住。

**判不准就不降级。** 没有 `files` 白名单、出现我们不建模的写法(`!` 取反、extglob、`{a..z}` 区间),或者存在安装期生命周期脚本(从 git 安装跑的是仓库本体而不是打包产物)——这些情况一律不降级。

**证据仍然在卡片上。** 不隐藏任何东西:这类发现记为 `exec_tooling`、`eval_tooling`、`base64_decode_tooling`、`net_server_tooling`、`token_env_tooling`,带同样的 `file:line` 证据,只是不计入等级。同一个行为同时出现在构建产物和开发脚本里时,两条都会报,不再互相遮盖。

**代价。** 全部卡片中有 13.6% 的敏感行为证据落在工具目录根。在 391 个插件的样本上用新旧两套规则各扫一遍(用同一份抓取的文件,避免把上游改动误算成规则改动):**22 个(5.6%)降了一级,没有一个升级**,C3 29%→24%。在受影响群体里再抽 248 个,26% 降级。只出现在不随包发布的脚本里的环境变量读取和外连域名也一并不再计入,所以少数插件会连降两级。

## 2026-08-19 · 我们审计了自己的标志,两条规则是错的

整个项目的立足点是"结论可被检验",所以我们真的去检验了:随机抽样标志,把每条引用的源码行拉出来逐条人工核对。结果发现两条规则在把插件没写过的代码算到它头上。

**注释被当成了代码。** 有个插件的文档注释写着*"本插件拦截的是工具调用面,**不是**插件内部代码(插件体内的 child_process/fetch/eval)"*——它因为这句"我不做这件事"的说明,被标记了 `exec`。现在匹配前会先把注释清空,并保留换行,所以行号依然准确。

**构建产物被当成了作者代码。** 这是更严重的一条。**全部带行号标志中的 32%** 位于 `lib/` 或 `dist/`——打包器产物,里面是内联进来的依赖。`eval` 高达 44%,base64 45%。抽样的 6 条 `eval` 里有 4 条指向同一个上游库 schemastery,而 dsh 自己就带着它:我们等于因为插件用了官方依赖而扣它的分。

构建产物中的发现现在标记为 `*_bundled`——照实说明代码确实在那里,但**不计入等级**,因为那不是作者写的。

**代价。** 在 327 个插件的样本上,49 个降了一级:C3 51%→43%,C0 7%→14%,C2+ 90%→81%。我们已公布的数字虚高了约 8 个百分点。报告里已加上更正说明。

### 本次同时发布

- **规则测试。** 扫描器此前一个测试都没有,而定时任务每天在重新评定数千个插件。现在有 10 组用例锁定决定等级的规则,CI 会在扫描前先跑一遍。
- **失败告警。** 扫描挂掉原本只会让站点悄悄停在旧数据上,现在会自动开 issue。
- **能力变化推送。** Atom feed 现在不只报"新扫描到的插件",还报"等级变了"或"新获得强能力"的插件——如果你已经装了它,这才是真正需要知道的。
- **扫描卡片移出 git。** 35MB 的逐仓库卡片原本每轮全量重写,现在放在 CI 缓存里;缓存丢失最多多跑一次全量扫描。

## 2026-08-18 · 首次发布

### 全生态覆盖

GitHub 搜索接口单次查询最多返回 1000 条,而 `dsh-plugin` 标签下有 7,000+ 仓库。改用**星标分桶 × 创建日期递归二分**的自适应切分来穷举,枚举出 6,942 个仓库(排除 fork 与归档)。

下载改走 codeload 直连而非 REST API——公开 tarball 免鉴权、不消耗每小时配额,否则 CI 里 7,000 次下载会直接撞上 1,000 次/小时的上限。

扫描改为增量:`pushed_at` 未变且上次成功的仓库直接复用缓存卡片,每轮设抓取预算。首轮全量之后,日常重扫成本极低。

### 两个影响结论准确性的修复

**流式解包**。原先按仓库体积设上限,导致一个 249MB 的仓库(含 555 个代码文件)被整个跳过。改成流式解压(`mode='r|gz'`)按解压字节预算停止后,跳过数从 43 降到 19,且剩下的全是"仓库里确实没有可扫描代码"。

**manifest 选取的确定性**。600 文件上限会截断 `package.json`,导致 monorepo 里报出哪个 manifest 取决于压缩包内的文件顺序——同一个仓库两次扫描可能给出不同结果。现在 `package.json` 不计入上限,并固定取路径最浅的那个。

这个 bug 一度让报告里一处关键例证不成立(我们原本写"声明为空 vs 实际 17 个服务",而那个"空"来自被截断后误读的子包 manifest)。修复后该段已改写为可复核的版本。

### 诚实度相关

- 下载失败与"仓库无可扫描代码"原本共用同一条错误信息,会把没扫到的仓库记成"没有代码",虚高覆盖率。现已分开。
- `data.json` 新增 `discovered` 字段,站点显示"生态共 N 个仓库,已扫描 M 个",而不是拿"我们有卡片的数量"当分母。
